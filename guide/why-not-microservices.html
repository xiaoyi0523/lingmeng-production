为什么不用微服务 ​

很多客户在评估社区平台时都会问：能不能拆成微服务？为什么灵萌是一个程序包，而不是十几个独立服务？

本文面向部署负责人、技术决策者与运营方，说明灵萌 V2 的架构选型——模块化单体（Modular Monolith），以及这样设计对私有化部署、多区域运营和功能按需开通的好处。

先分清两个概念 ​

概念是什么灵萌的情况
微服务把系统拆成多个独立进程/服务，各自部署、独立数据库，通过网络 RPC/消息通信未采用
模块化单体一个可部署单元（一个 lingmeng 二进制），内部按业务划分子模块，边界清晰、统一装配当前方案
功能模块（商业）圈子、外卖、AI、优惠券等可按授权在后台开关这是产品能力开关，不是微服务拆分

灵萌的「30 个业务模块」是代码与职责划分，对外交付时仍是一套服务 + 一个安装包，而不是 30 个容器。

为什么不采用微服务 ​

1. 业务强联动，拆服务代价高 ​

灵萌不是「几个互不相干的 CRUD 系统拼在一起」，而是典型的社区 + 交易 + 触达闭环：

  • 发笔记 → 评论/审核 → 通知推送 → 搜索索引
  • 下单 → 统一订单 → 微信支付/支付宝 → 资金账本 → 退款/提现
  • 私聊/群聊 → WebSocket 实时消息 → 红包/转账仍走支付链路
  • 外卖/跑腿 → 订单、骑手、地图、支付多条线在同一事务链上

这些路径需要强一致或清晰的事务边界。若拆成微服务，一次用户操作往往要跨 3～5 个服务，要么接受分布式事务的复杂度，要么接受最终一致带来的对账、补偿与客诉成本——对校园/区域社区场景来说，投入产出比很低。

灵萌在单体内部用一套统一基建解决模块协作，核心原则是：同类能力只实现一次，各业务模块复用，禁止各搞一套。若拆成微服务，这些「统一」往往要在每个服务里重复建设或再建中台，运维与一致性成本更高。

类别统一模式解决什么问题
身份与权限统一用户体系C 端用户、商家、骑手、管理员共用账号模型与登录会话，不按端复制一套用户服务
统一授权门面后台菜单权限、圈子权限、区域权限、特权能力从同一套入口校验
统一操作人上下文后台「谁在操作」一次注入，审计与敏感操作可追溯
交易与资金统一订单外卖、会员、团购、闲置等所有可支付业务共用订单模型与状态流转
统一支付微信/支付宝回调只进一条链路，业务层不各自对接支付网关
资金账本余额变动、流水、对账在同一套账本规则下完成
对账与补偿支付/订单异常有统一登记与补偿任务，而不是各模块自行兜底
内容与社区统一评论笔记、活动、商品等全站共用一套评论能力，运营规则一致
统一审核中心发帖、头像、商家入驻等进同一审核台，不用每个业务单独审
统一内容联动跨模块挂载（如笔记挂商品、活动挂抽奖）走统一关联，而非硬编码外键
区域与配置统一区域配置全站默认 + 区域覆盖三级兜底，多校区规则可独立又不分裂部署
区域内容解析笔记、评论等内容归属哪个校区，有统一解析规则
消息与触达统一通知站内信、模板消息、订阅消息变量从同一套通知引擎发出
即时消息 WebSocket私聊、群聊、红包/转账与支付链路在同一进程内衔接
统一变量注入通知、短信、模板里的 {昵称} {订单号} 等统一解析，不散落拼字符串
可靠性与异步业务事件 Outbox跨模块联动（如发帖 → 搜索引 → 发通知）异步但可靠，不丢事件
统一幂等重复点击、重复回调、重复投递由统一入口拦截
统一分布式锁抢单、库存、并发写等临界区用同一套锁语义
统一状态机订单、活动、审核等状态流转规则集中声明，避免各模块自定义状态
统一缓存热点数据读写与失效策略一致，减少脏读与穿透
搜索与运营统一搜索索引内容变更经 Outbox 同步到 Meilisearch，业务不直连搜索引擎
统一任务引擎签到、成长值、活动任务等玩法配置化，不写死在单个模块里
统一导出后台列表导出走统一异步任务，而不是每个模块单独做导出
AI 与开放AI 业务中台多模型、配额、场景路由、异步任务统一收口
对外开放流对外 Webhook / 开放 WebSocket 从统一出口推送，便于对接企微、钉钉等

这也是模块化单体能够「功能很多，但部署仍是一个包」的关键：不是 30 个模块各写各的，而是 30 个模块共享上述统一能力。

2. 私有化部署是主场景，运维要简单 ​

灵萌大量客户是宝塔 + 单机/少量服务器私有化部署：

  • 上传 zip → 进程守护运行 lingmeng
  • MySQL + Redis 即可跑通核心能力
  • 可选 Meilisearch、Gorse 等外围组件，但业务核心仍是一个二进制

微服务典型落地需要：容器编排（Kubernetes 等）、服务发现、配置中心、独立日志/链路追踪、多套监控告警、多服务滚动发布与版本兼容。这与「学校 IT 一台云主机、运营方自行维护」的现实不匹配。

3. 团队与交付形态：按模块授权，而非按服务拆团队 ​

灵萌的商业模型是按功能模块授权（见 我的模块），客户开通圈子、外卖、AI 等能力，而不是购买「用户微服务实例 × 3 副本」。

代码里的 30 个业务包 + 统一 pkg 基建，是为了研发可维护；对客户而言，应是：

  • 未开通的模块在后台不可见或不可用
  • 已开通的在同一套 API、同一套客户端里无缝使用

用微服务拆分不会增加客户感知价值，却会增加部署文件、端口、健康检查和故障排查 surface。

4. 数据一致性与资金类业务 ​

支付、余额、优惠券核销、推广员佣金、提现等，要求：

  • 同一 MySQL 事务内完成状态变更
  • 幂等、锁、对账有统一入口（账本、订单、RunOnce 幂等）

微服务若按服务拆库，跨库一致性要额外建设 Saga/TCC、对账任务与人工运维流程。灵萌选择逻辑分模块、物理同一库（可配置分库扩展，但非默认微服务形态），优先保证正确性，再谈水平扩展。

5. 性能与实时性 ​

即时消息（WebSocket）、通知推送、AI 流式输出等，需要长连接与低延迟。单体内部函数调用 + 共享 Redis，比跨服务 HTTP/gRPC 更直接；必要时通过 worker 进程分担异步消费（见下文），而不是默认拆成十几个网络服务。

灵萌实际采用什么架构 ​

模块化单体 + 统一基建 ​

层次作用
30 个业务模块圈子、消息、支付、外卖、AI… 各管一块，统一五层结构（接口 → 服务 → 仓储 → 模型 → DTO）
pkg/ 横切能力上表中的缓存、锁、幂等、状态机、区域配置、通知、账本等只实现一次
bootstrap/wiring启动时装配依赖、注册跨模块回调，边界清晰但不跨进程
架构守卫（CI）禁止跨模块直连仓储、禁止 Handler 写 SQL 等，防止「单体变泥球」

对外能力清单见 功能模块总览；技术结构见 架构概览。

一种「轻量拆分」：API 与 Worker，不是微服务 ​

灵萌支持同一套代码以不同启动模式运行，用于分担负载，但仍是一个代码库、同一套配置、同一数据库：

模式用途
full默认：HTTP API + WebSocket + 定时任务 + 队列消费
worker仅跑后台任务与健康检查（如不对外提供业务 HTTP）
http_only只提供 API，暂不跑部分消费者

这是「进程级分工」，便于将来把 worker 放到第二台机器；不是按业务域拆成订单服务、用户服务等多个独立产品。

异步与可选组件 ​

对耗时、可降级的能力，用事件 Outbox、消息队列、定时任务异步处理，而不是强行拆微服务：

  • 搜索索引同步 → Outbox + Meilisearch（可选）
  • 推荐 → Gorse（可选）
  • 通知、模板消息 → 队列与 worker

这种架构带来的好处 ​

对你（部署与运营） ​

好处说明
部署简单一个安装包、一个守护进程、MySQL + Redis，快速部署 即可上线
排障路径短日志、配置、版本在一处；不用跨十几个服务查链路
升级可控替换二进制 + 内嵌 SQL 迁移，系统更新 流程清晰
按模块开通未买的功能不占菜单，已买的在同一 App/小程序里连贯使用

对业务正确性 ​

好处说明
交易链路统一所有支付走统一订单、统一支付与资金账本，减少「A 模块扣款、B 模块没记账」
身份与权限统一用户、商家、骑手、管理员同一套账号与授权体系，客户端与后台规则一致
审核/评论/联动统一全站一套评论、一套审核中心、一套内容挂载，运营规则一致
多区域可配置全站默认 + 区域覆盖，一套系统服务多个校区（见 区域管理）

对长期演进 ​

好处说明
模块边界清晰代码按域分包，后续若真需拆服务，也有明确切口（而非历史泥球）
统一规范与 CI架构守卫、统一 DTO/列表/权限门面，降低 30 个模块协作成本
可选 scale-outworker 独立进程、Redis 队列、只读扩展等，按量加机器而非一步到位上 K8s

什么时候才需要考虑微服务 ​

微服务适合：超大流量、超大团队、域之间几乎无强事务、且具备专职平台/SRE 团队的产品。例如全国性超大型 C 端互联网，独立团队维护订单中台、用户中台。

灵萌的目标场景是：

  • 校园 / 区域社区
  • 私有化或少量云主机
  • 运营与技术人力有限
  • 功能多但单站 QPS 通常在单体 + Redis + MySQL 优化可承受范围内

若未来单客户出现明确瓶颈（如 IM 连接数、搜索写入量），灵萌的演进路径通常是：

  1. 先水平加 worker、读写分离、缓存与索引优化
  2. 再考虑把个别域（如搜索、推荐）外置为独立组件——仍与现有 Outbox/可选部署文档一致
  3. 只有在客户基础设施与团队都就绪时，才评估完整微服务化

而不是默认让每个客户一开始就维护一套微服务集群。
